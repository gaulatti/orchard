The original user brief, “Goal draft: complete Orchard for Windows”, is the
source of the completion requirements. Its retained attachment has SHA-256
`6d0164110307247ee2135d5222b4ae07c46b3a5afa917e2a24a4a344a263ac0d`.
The later [component-library scope correction](library-scope.md) excludes

The brief requires the fixed inventory, public component APIs, variants and
states, Windows interaction conventions, token-derived appearance, catalog
coverage, regression and runtime verification, accessibility metadata, measured
collection performance, independent NuGet consumption, accurate documentation,
remote-main delivery and versioned package/catalog artifacts. Native ARM64
runtime remains a separate requirement from ARM64 compilation. The current
instruction to avoid Actions remains in effect; CI evidence must retain its
actual source and age.

## Visual and behavior evidence

Review every component against its pinned reference across its applicable
variants, sizes, themes and interaction states. Verify typography, spacing,
geometry, colors, borders, radii, icons and motion. Windows defaults must not
replace Bleecker's visual language. Native keyboard, pointer, focus, selection,
scrolling and accessibility behavior must preserve the component's purpose.
Token assertions, compilation and nonblank screenshots alone cannot establish
acceptance.

Native expectations incorporate the user's explicit corrections: Orchard dark
tokens for Data Table's dark body, working pointer deletion in Media Library,
the entire narrow Command Spotlight shortcut hint hidden, and the requested
Hero Carousel global-arrow/inactive-slide input behavior. Preserve the frozen
web captures and test these corrected native outcomes directly. A source image
that contains the intentionally removed shortcut separator cannot itself be
the native expected image.

The brief does not specify byte-identical browser/native raster output or a
numeric whole-image tolerance. Existing zero-tolerance image comparisons retain
their thresholds and actual failures. They provide diagnostics for rendered
differences and stronger evidence where exactness is an explicit experimental
claim. They do not replace a component's complete visual/behavior acceptance
review. Explain each observed visual difference using the actual native
contract; do not approve a wrong token, missing state, stock style, clipping,
unreadable text or broken interaction merely because its image error is small.

The source-exact overlay renderer remains an unaccepted internal experiment.
Its capsule, oval, fractional and other image failures stay recorded. Promotion
still requires its declared geometry, ownership and image contracts. Completing
that experiment is distinct from proving that the public component satisfies
the user's requested Windows design-system contract.

Every inventory entry needs current evidence for its required behavior and
visual states, catalog fixtures, appropriate regression tests, runtime and
package boundaries, and its applicable accessibility, motion, scaling and
performance checks. Inspect what each test actually covers. Historical previews
and another architecture's build cannot establish fresh native runtime success.

Record build, runtime, visual, consumer, performance and delivery results
separately. An entry becomes accepted only after all its required gaps are
closed with evidence. Both fictional Monitoring and Editorial compositions
remain required. The current inventory remains 112 in progress, zero pending,
zero accepted; 100% means entries started. No completion estimate is derived
from that number.
